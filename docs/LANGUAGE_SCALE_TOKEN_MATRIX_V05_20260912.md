# AIRP v0.5 语言 × 代码规模 Token 矩阵

本实验比较两种向模型交付代码上下文的协议：基线返回搜索命中位置和完整目标文件；AIRP 使用一次自然语言 `task_context` 返回预算内的符号上下文。两组完整响应都由 `o200k_base` 计数。每个文件包含 24 个可解析符号，任务要求定位一个唯一退款函数并恢复函数中的答案标记。

只有 AIRP 首个锚点等于预期符号、且上下文包含答案标记时，单元格才计为有效。40 个单元格全部通过。数值计算为 `100 × (1 - AIRP 响应 Token / 基线响应 Token)`。

全矩阵平均减少 56.54%，最低 47.87%，最高 63.03%。各语言均值为：Python 48.95%、TypeScript 61.55%、Go 55.94%、Rust 62.42%、Java 54.75%、C# 54.27%、C 58.20%、C++ 58.00%、Ruby 48.62%、PHP 62.65%。

## 解释

收益在同一种语言的四档规模间基本稳定。这说明持久索引阻止了仓库总规模进入模型上下文，但 Token 减少的主要来源是从完整文件缩小到目标符号。语言间差异主要由模板语法、完整文件 Token 密度以及 AIRP 固定响应元数据共同造成，不能解释为某种语言的真实项目一定更节省。

2 文件、每文件 8 个符号的前置冒烟实验曾出现 -28.03% 到 2.45% 的收益：目标文件非常小时，AIRP 的结构化响应元数据可能超过直接读取文件的成本。因此插件后续应增加“小文件旁路”，在预计完整文件更便宜时直接返回文件，而不是强制生成上下文包。

## 适用边界

这是确定性的上下文检索协议实验，不包含模型推理、工具选择、修改、测试重试或最终答案 Token，不能替代完整 Agent A/B。合成任务具有唯一、词面明确的目标，并未覆盖同义表达、跨模块行为、动态分派、宏、生成代码和真实缺陷修复。结果证明各语言后端能够在这些规模下正确缩小上下文；真实产品结论仍需在相同任务成功率约束下运行真实仓库与固定模型的配对实验。
