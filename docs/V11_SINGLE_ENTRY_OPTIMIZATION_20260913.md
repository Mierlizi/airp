# AIRP 单入口与选择性启用优化

## 结论

本阶段显著降低了插件自身开销，但没有让约 1,850 行项目上的简单事实查询获得净 Token 节省。相同 12 题安装态实验中，旧版强制 AIRP 为 Baseline 的 3.53 倍；单入口版降为 2.35 倍。它仍不适合对所有代码任务强制启用，因此最终 Skill 改为按任务选择：简单单文件或精确值查询使用普通搜索，预计需要多次源码读取或结构关系时才调用 AIRP。

## 实现

- MCP 工具模式从 7 个收敛为一个 `airp`，通过 `operation` 访问查询、关系、编辑、验证和事务能力。
- `operation=context` 在一次调用中自动创建或刷新索引，删除每题显式 `airp_index` 轮次。
- Skill 正文缩短，并明确简单查值任务不启用 AIRP。
- Python 索引新增模块级 `Assign` 与 `AnnAssign`，修复 `GRAPH_SCHEMA`、`IGNORED` 等模块数据不可检索的问题。
- 大函数超过预算时，保留签名并围绕任务词返回聚焦源码窗口，避免整个符号因预算不足被丢弃。
- 图模式版本升至 4；旧索引会自动判定过期并刷新。
- 插件 `defaultPrompt` 从 4 条降至宿主允许的 3 条。

## 同一真实源码安装态 A/B

数据文件为 `benchmarks/runs/integrated-real-source-v13.json`。两个条件各 12 次，共 24 条记录；完整性门禁与 12/12 AIRP MCP 执行门禁均通过。AIRP 条件被实验提示强制调用，用于测量最坏的“所有任务启用”策略。

| 指标 | Baseline | 单入口 AIRP | 变化 |
|---|---:|---:|---:|
| 输入 Token | 413,290 | 973,980 | +135.66% |
| 输出 Token | 2,576 | 5,079 | +97.17% |
| 总 Token | 415,866 | 979,059 | **+135.43%** |
| 每题平均总 Token | 34,656 | 81,588 | +135.43% |
| 未缓存输入加输出 | 69,754 | 267,123 | **+282.95%** |
| 总墙钟耗时 | 352.783 秒 | 423.843 秒 | **+20.14%** |
| 工具事件 | 16 | 23（12 MCP + 11 命令） | +43.75% |
| 语义答案通过 | 11/12 | 11/12 | 0 个百分点 |

相对旧版有效实验 v11，AIRP 工具事件从 48 降为 23，减少 52.08%；AIRP 总 Token 从 1,517,774 降为 979,059，减少 35.49%。由于两轮 Baseline 本身有随机波动，更稳妥的比较是“相对各自 Baseline 的增幅”：从 +252.58% 降到 +135.43%，仍未转正。

## 信息丢失与修复后验证

v13 中 AIRP 唯一错误来自大函数聚焦窗口没有带上 `full-file-cost-bypass` 前方的 intent 条件，属于 1/12 的检索证据遗漏。Baseline 唯一错误来自答案格式词误判，错误题与 AIRP 不同。

扩大聚焦窗口后：

- 本地冻结问题逐题审计能恢复 12/12 所需证据。
- 新增两项聚焦摘录回归测试，完整测试为 41/41 通过。
- 对原遗漏问题做 3 次独立安装态配对重复，AIRP 为 3/3，Baseline 为 3/3；数据在 `benchmarks/runs/focused-excerpt-postfix-v14.json`。

这证明已修复已知遗漏，但 3 次重复不足以宣称总体信息丢失率为零。最终候选尚未再次执行完整 12 题，因此完整 Agent 准确率仍应引用 v13 的 11/12，并同时注明修复后的针对性结果。

## 为什么仍然增加 Token

一次 MCP 调用会产生工具返回后的额外模型轮次。Skill 被加载时还可能产生一次说明文件读取轮次；其正文已经很短，但新一轮仍会重复携带宿主固定上下文。对于只需一次 `rg` 或一次文件读取的题，AIRP 无法靠减少源码正文抵消这些固定成本。

修复后的 3 次重复也显示这个边界：AIRP 总体仍比 Baseline 多 41.60%，但唯一没有读取 Skill 文件的重复中，AIRP 为 45,936 Token，Baseline 为 47,892 Token，AIRP减少 4.08%。这是单个重复，不能作为稳定收益率，却直接说明额外 Skill 读取轮次是主要波动源。

## 当前适用规则

值得启用：

- 预计需要搜索和读取多个文件；
- 需要调用者、依赖、影响范围或测试候选；
- 大文件中只需要少量相关函数或配置；
- 已有热索引且后续会连续处理相关任务。

不值得启用：

- 一个明确符号、常量或默认参数的一次性查值；
- 已知文件中的短代码读取；
- 小仓库中普通搜索一次即可完成的任务。

下一阶段应使用大型真实仓库和多文件任务验证选择性路由的盈亏平衡点，而不是继续在简单查值任务上强制调用 AIRP。
