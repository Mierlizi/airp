# AIRP Context Compiler A/B 初步实验

日期：2026-09-12

## 结论

在 3 个 AIRP 自身代码理解任务、每个条件重复 2 次的只读配对实验中，AIRP Context Compiler 在答案正确率相同的情况下，将模型输入 Token 从 95,378 降至 79,840，减少 **16.29%**；输入与输出合计从 96,759 降至 81,194，减少 **16.09%**。

这是 Context Compiler 的小样本消融结果，不是完整 Coding Agent 插件的商业性能结论。

## 实验设置

| 项目 | 设置 |
|---|---|
| 模型 | `gpt-5.6-luna` |
| 推理强度 | `low` |
| 任务 | 3 个 Python 代码理解问题 |
| 重复 | 每个任务、每个条件 2 次，共 12 次推理 |
| Baseline | 提供目标所在的完整 Python 文件 |
| AIRP | 提供 `airp_context` 在 8,000 UTF-8 字节预算内选择的完整符号 |
| 控制 | 相同模型、问题、回答要求、工作目录；禁用用户配置和工具调用；只读执行 |
| 顺序 | 两轮反转每对条件的先后顺序 |
| 验收 | 每个问题预设事实要点；保存模型原始回答并检查同义表达 |

任务覆盖 Context 预算与省略行为、事务 commit 条件、AST 调用边提取行为。第一轮的词面检查曾把“源码指纹”和“不会被记录”等正确同义表达误判为失败；保留原始回答，人工按源码核对后扩展同义词组，最终两组均为 6/6 正确。后续正式实验应在运行前冻结更结构化的验收器，避免事后调整。

## 汇总结果

| 指标 | Baseline | AIRP | 变化 |
|---|---:|---:|---:|
| 正确任务 | 6/6 | 6/6 | 持平 |
| 输入 Token | 95,378 | 79,840 | **-16.29%** |
| 非缓存输入 Token | 35,474 | 26,080 | -26.48% |
| 输出 Token | 1,381 | 1,354 | -1.96% |
| 输入+输出 Token | 96,759 | 81,194 | **-16.09%** |
| 提供的上下文字节 | 90,104 | 21,400 | -76.25% |
| 总耗时 | 69.95 秒 | 71.94 秒 | +2.84% |

缓存输入会受前缀缓存命中影响，两轮中各条件的缓存量并不恒定，因此非缓存 Token 降幅只作观察值。总输入 Token 在两轮中对每个条件完全复现，更适合作为本次初步结论。

按任务观察，输入 Token 降幅分别约为 20.84%、21.53% 和 4.56%。第三项目标文件本身较小，AIRP 可移除的无关内容有限，说明收益明显依赖文件大小及相关代码密度。

## 能说明什么

结果支持一个有限结论：当普通 Agent 已定位目标但倾向读取完整文件时，AIRP 选择完整相关符号可以减少模型实际收到的输入 Token，同时保持这 3 个问题的回答质量。

上下文文本减少 76.25%，最终输入 Token 只减少 16.29%，因为 Codex 每次运行还有系统提示、工具定义及其他固定上下文。优化仓库文本无法消除这些固定开销。输出 Token 基本不变，耗时也没有改善。

## 不能说明什么

- 没有测量完整插件工作流中的 MCP schema、索引、查询和事务调用开销。
- 没有执行真实 Bug 修复、跨文件编辑、重试或隐藏测试。
- Baseline 是“完整目标文件”，并不覆盖 Agent 通过 grep 自行构造更小上下文的能力。
- 任务来自 AIRP 自身代码，只有 3 个问题和 2 次重复，不具统计显著性或外部代表性。
- 没有 API 账单数据，因此不能将 Token 降幅直接换算为现金成本降幅。

## 后续正式验证

下一阶段应冻结 20–50 个来自多个真实 Python 仓库的任务、隐藏验收测试和预注册指标，比较普通文件/搜索工具与完整 AIRP 插件。主要指标应为 Cost per Successful Task；同时记录输入与输出 Token、缓存 Token、工具调用、文件读取量、重试、延迟和任务成功率。
