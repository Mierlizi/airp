# AIRP 普适性与适用任务比例边界

> 2026-09-13真实源码安装态A/B显示，当前版本在12个只读任务上总Token增加252.58%。本文中的正向数字是压缩载荷毛收益；插件净收益请以`docs/V10_REAL_SOURCE_INSTALLED_AGENT_AB_20260913.md`为准。

## 结论

当前没有足够证据给出“AIRP值得用于全部代码任务中的X%”这一总体比例。现有真实模型实验完整覆盖的是一个任务族：合成Python代码中的静态直接依赖只读理解。它覆盖了约528至32,370个原始代码Token，但扩大代码量不等于扩大任务类型。

因此，当前可报告的是条件覆盖率，而不是市场总体覆盖率：

- 在已测任务族内，6个代码量档位均保持预定义必要信息0/1,300丢失。
- 若把“总模型Token至少减少10%”定义为值得启用，约1,539至32,370代码Token的5个档位达到门槛；约528 Token档只有3.15%，不值得为了节省Token强制启用。
- 不能把5/6档写成83%的代码任务，因为档位没有按真实开发任务频率加权。
- 32和64依赖档虽然Token降幅达到55.56%和69.38%，但模型答题出现质量风险，因此“大任务自动启用”还必须加入证据分块与结果验证。

## 按任务类型判断

| 代码任务 | 当前建议 | 理由与证据状态 |
|---|---|---|
| 仓库问答、符号定位、定义查找 | 值得使用 | 与已测静态只读理解最接近；相关代码超过约1,500 Token后总Token收益超过10% |
| 调用链、依赖关系、影响范围分析 | 值得试用 | 插件具备图与调用边能力，但尚未完成真实任务类型A/B |
| 修改前的文件/函数定位 | 值得作为前置步骤 | 能压缩读取阶段；不能把读取收益等同于整项编辑任务收益 |
| 多文件缺陷修复、重构、功能开发 | 条件使用 | 定位阶段可能受益，编辑、测试、失败重试尚无规模化实验 |
| 测试编写与测试失败分析 | 条件使用 | 静态源码上下文可受益，运行日志与动态状态不在当前索引证据内 |
| 小于约500代码Token的单文件问题 | 通常不值得 | 当前总Token只减少约3.15%，固定系统上下文占主导 |
| 新建独立函数、算法题、短代码补全 | 通常不值得 | 几乎没有仓库检索和跨文件上下文可压缩 |
| 反射、运行时注入、动态分派、生成代码 | 暂不建议依赖 | 静态图可能缺边，必要信息丢失审计尚未覆盖 |
| UI视觉检查、部署、环境和外部服务故障 | 不属于主要适用范围 | 核心证据不在静态代码关系图中 |

## 建议的自动启用门槛

插件不应以“安装后每个任务都调用”的方式追求普适性。路由器应同时满足以下条件才自动启用：

1. 任务需要读取现有仓库，而不是从零生成短代码。
2. 预计相关原始代码不少于约1,500 Token；低于该值时预计总Token收益不足10%。
3. 任务可以由符号、导入、调用或词面关系定位。
4. 静态证据完整性置信度达到门槛；存在动态调用时回退到文件读取或运行时工具。
5. 依赖扇出达到32以上时分块交付并增加计算/修改结果验证，避免模型一次处理过长事实列表。

这套门槛只能决定某个任务是否是AIRP候选，不能代替端到端A/B验收。

## 为什么不能从单一基准推算市场比例

“全部代码任务”没有统一的任务分布。公开基准分别测量不同切面：

- [SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/)包含500个工程师确认可解的真实GitHub问题，但OpenAI后来[报告其部分测试会拒绝正确方案](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)，因此单独使用它也不能代表全部开发工作。
- [RepoBench](https://arxiv.org/abs/2306.03091)将仓库级任务拆成检索、代码补全和完整流水线，说明上下文检索只是代码任务的一部分。
- [DependEval](https://aclanthology.org/2025.findings-acl.373/)覆盖2,683个真实仓库、8种语言，以及依赖识别、仓库构建和多文件编辑三类任务。
- [SWE-QA](https://aclanthology.org/2026.findings-acl.402/)包含720个仓库问答，覆盖意图理解、跨文件推理和多跳依赖。
- [RepoDebug](https://aclanthology.org/2025.findings-emnlp.1294/)覆盖8种语言的缺陷识别、定位和修复；[FEA-Bench](https://aclanthology.org/2025.acl-long.839/)则覆盖83个仓库的1,401个功能开发任务。

这些数据集的采样目标不同，不能简单拼接成一个开发者日常任务百分比。可信的总体比例必须先指定目标用户群和任务日志分布。

## 得到真实“X%值得使用”所需的实验

从目标开发者的连续任务日志中随机抽样至少300项，先按下列任务族分层：只读理解、定位/影响分析、缺陷修复、重构、功能开发、测试、文档/配置、构建/部署。每项运行Baseline和AIRP，并冻结验收条件。

单项任务只有同时满足以下条件才计为“值得使用”：

- 总模型Token至少减少10%；
- 任务必要信息丢失率不高于1%；
- 端到端验收结果不劣于Baseline；
- 耗时增加不超过10%，或Token成本收益足以抵消延迟。

最终比例为满足四个门槛的任务数除以全部抽样任务数，并按真实任务频率加权，报告95%置信区间。300项样本在比例接近50%时的简单随机抽样误差约为正负5.7个百分点；若要更窄区间需要更多任务。

在完成该实验前，任何“覆盖全部代码任务的20%、50%或80%”都只能是商业假设，不应作为插件实测性能发布。

## 当前产品定位

AIRP当前适合定位为“对仓库上下文较重任务按需启用的上下文压缩与证据检索层”。它还不是覆盖所有代码任务的通用代理插件。普适化的正确方向是增加可靠路由、动态证据回退和分阶段验证，而不是让所有任务无条件经过同一压缩流程。

## 插入Agent后的净Token边界

仓库有几十万行并不意味着一次任务会把几十万行送进模型。AIRP的收益由“该任务原本需要交付给模型的相关代码量”决定。十万行仓库中的单函数问题仍可能只有约500代码Token；五千行仓库中的跨模块问题则可能需要数万代码Token。

当前真实模型A/B通过`--ignore-user-config`保持两组系统环境一致，再分别注入完整与压缩代码响应。这能测量上下文压缩的毛收益，但没有完整计入安装插件后新增的Skill说明、MCP工具模式以及额外工具调用。当前完整`SKILL.md`约753个`o200k_base` Token；MCP实际工具模式开销尚未通过宿主用量记录独立测量，不能把实现源码Token当成工具模式Token。

| 任务相关原始代码 | 当前压缩毛节省/题 | 若新增固定开销750 Token后的余额 | 若新增固定开销1,500 Token后的余额 |
|---:|---:|---:|---:|
| 528 Token | 413 | −337 | −1,087 |
| 1,539 Token | 1,557 | 807 | 57 |
| 4,066 Token | 2,997 | 2,247 | 1,497 |
| 8,109 Token | 8,764 | 8,014 | 7,264 |
| 16,196 Token | 17,549 | 16,799 | 16,049 |
| 32,370 Token | 35,212 | 34,462 | 33,712 |

750与1,500只是开销敏感性场景，不是实测插件模式开销。它们说明自动路由的重要性：小任务可能净增加Token，约4,000代码Token以上开始有较明显余量，约8,000以上则对合理固定开销较不敏感。

综合Token还可用近似关系理解：若原始代码上下文占Agent总Token的比例为`f`，AIRP把代码缩短约90%，则忽略固定插件开销时，总体上限约为`0.9 × f`。代码只占总消耗20%时，理论总收益约18%；代码占50%时约45%。推理、答案、测试日志和失败重试不会因为代码压缩自动同比下降。

最终净收益需要新增“真实安装态Agent A/B”：Baseline禁用AIRP，实验组正常加载Skill与MCP；两组在同一真实任务上自主搜索、编辑和测试，统计完整会话Token、调用轮数、成功率及索引成本。完成前应把当前数字称为上下文压缩毛收益。
