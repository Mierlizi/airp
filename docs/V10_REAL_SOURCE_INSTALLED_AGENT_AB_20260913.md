# AIRP真实源码安装态Agent A/B

用户于2026-09-13明确允许为本实验向模型发送当前项目源码。发送范围限制为`airp`、`tests`、`examples`、`plugins`、`README.md`和`pyproject.toml`；本地扫描未发现密钥、环境文件、证书或凭据。实验不发送Git历史、虚拟环境、缓存、构建产物或基准运行目录。

## 为什么需要这次实验

此前实验把完整代码响应或AIRP压缩响应直接注入相同的模型环境，测量的是上下文压缩毛收益。它没有让Agent真实加载Skill、MCP工具模式、执行索引和自主决定查询轮次，因此不能回答安装后的会话净Token。

## 方法

- 当前真实项目中11个Python文件，约1,850个非空代码行、22,639个代码Token。
- 12个冻结答案的源码事实问题，Baseline和AIRP各运行一次，共24次模型调用。
- Baseline加载普通Codex工具但忽略用户插件配置；AIRP加载已安装的Skill与MCP。
- 两组最多进行3次源码查询；AIRP每题先调用一次`airp_index`。
- 使用两个持久隔离副本，每个副本首题建立冷索引，后续五题增量复用。
- 所有36次AIRP MCP调用均成功完成；实验完整性与MCP执行门禁通过。
- 严格格式与语义答案分开判定。单位后缀和省略`ast.`前缀不计为语义错误。

## 准确率与证据问题

AIRP真正答错的两题是`GRAPH_SCHEMA`值和`IGNORED`集合数量。这两者都是模块级赋值；当前Python索引主要把函数、异步函数和类作为符号，没有把模块常量作为独立可检索符号。Baseline可以直接搜索文件，因此两题均正确。

其他严格格式失败包括附加“秒/条/bytes/ms”单位或返回`Name|Attribute`而不是`ast.Name|ast.Attribute`，语义上正确，未计入语义失败。

## 根因

1. Skill正文会通过一次命令读取，形成额外模型轮次。
2. Skill要求每个新任务先调用`airp_index`，即使索引增量复用，工具响应和下一轮固定上下文仍产生Token。
3. 一个源码问题通常需要索引加1至3次查询；AIRP平均每题4.00个工具事件，Baseline为1.42个。
4. 七个MCP工具模式扩大每轮固定输入；当前实验没有单独拆出精确模式Token，但完整会话数据已包含它。
5. `sufficient=false`或召回不精确会推动Agent继续查询，单次响应压缩收益被额外轮次覆盖。
6. 模块级常量缺失造成两项真实证据覆盖失败。

## 当前结论

在这个真实项目的12个只读事实任务上，当前安装态AIRP没有减少综合Token，而是使用Baseline的3.53倍。此前3.15%至69.38%的数字仍可描述“已提供正确锚点后的压缩载荷毛收益”，不能描述插件安装后的Agent净收益。

这项实验仍不足以推断十万行仓库：项目只有约1,850行Python代码，Baseline用一至三个普通搜索/读取命令即可解决问题。大型仓库中AIRP可能减少更多搜索轮次，但在重测前，不能宣称它会产生净收益。

## 下一步优化门槛

1. 将索引检查和任务上下文合并成一次自动操作，移除每题显式`airp_index`轮次。
2. 将七个MCP工具收敛为一个紧凑动作工具，减少模式输入。
3. 缩短Skill并避免每个任务通过shell读取完整说明。
4. 为模块常量、赋值和配置项建立可检索符号。
5. 当第一次上下文已包含答案时阻止重复或平行查询。
6. 优化后必须在相同12题上把AIRP总Token至少降到Baseline以下，再扩展到大型真实仓库。
