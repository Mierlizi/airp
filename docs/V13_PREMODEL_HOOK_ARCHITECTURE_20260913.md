# AIRP 预模型上下文架构

## 要解决的根因

旧架构压缩了工具响应，却没有消除 MCP 的固定时序成本：模型先决定调用工具，AIRP 返回结果，然后模型再次运行才能回答。短任务中，第二次模型输入会重新携带会话、系统说明、Skill 和工具定义，因此总 Token 可能不降反增。

## 新执行路径

```text
用户问题
  → UserPromptSubmit 本地 Hook
  → 增量索引 + 任务分类 + 自适应检索
  → 只把紧凑证据注入 developer context
  → 第一次模型请求直接回答或继续编辑
```

任务覆盖不再依赖“不建议调用 AIRP”的门槛。只要当前目录包含受支持源码且问题属于代码任务，AIRP 都会在首次推理前运行：

- 单文件、单符号和精确事实：2,200 字节 narrow 包；
- 多对象任务：4,000 字节 balanced 包；
- 调用链、依赖和影响分析：6,000 字节 broad 包；
- 非代码对话：不注入无关内容。

这个分类控制证据量，而不是决定 AIRP 是否服务某类代码任务。MCP 仍保留为独立兼容接口，但默认插件不加载它，因此不会增加工具 schema，也不会诱发重复的源码查询。

## 安全和失败行为

Hook 只扫描 AIRP 支持的源码文件，复用 `.airp` 增量索引，并把选中的源码片段交给当前模型。检索失败时静默退化为普通 Agent 行为，不阻断用户任务。安装后必须由用户审查并信任 Hook，这是 Codex 对插件生命周期脚本的宿主级要求。

## 验证边界

单元测试验证代码任务门控、自适应证据生成、限定名精确排序、Hook JSON 协议、非代码静默路径和去除 receipt/routing 元数据。当前共 47 项测试通过，插件与 Skill 官方校验器均通过。

### 12 题确定性负载审计

使用安装态实验的 12 个真实源码问题与 `o200k_base` 精确计数：

| 指标 | MCP JSON | 预模型 Hook | 变化 |
|---|---:|---:|---:|
| 上下文负载 Token | 6,024 | 4,614 | **−23.41%** |
| sufficient | 12/12 | 12/12 | 不变 |
| AIRP 覆盖 | 12/12 | 12/12 | 不变 |

原始数据：[hook-payload-v16.json](../benchmarks/runs/hook-payload-v16.json)。这里只计算模型接收的 AIRP 负载，不含被新架构消除的 MCP 后续模型轮次。

### 2 题真实 Agent 预实验

同一模型、同一真实源码、交叉执行顺序；baseline 用普通源码读取，premodel 把真实 Hook 输出放入首次请求。索引耗时计入延迟，注入证据计入模型输入 Token。

| 指标 | 普通读取 | 预模型 AIRP | 变化 |
|---|---:|---:|---:|
| 总模型 Token | 72,272 | 43,300 | **−40.09%** |
| 正确率 | 2/2 | 2/2 | 持平 |
| 源码命令调用 | 3 | 1 | **−66.67%** |
| 总耗时 | 44.28 s | 26.56 s | **−40.02%** |

原始数据：[premodel-hook-probe-v16.json](../benchmarks/runs/premodel-hook-probe-v16.json)。样本只有两题，不能把 40.09% 当作总体效果。第一题在精确限定名排序修复前执行并发生一次补充读取；修复后本地覆盖检查已从 partial 变为 sufficient。

完整 12 题、24 次配对实验脚本已经就绪：[run_premodel_hook_ab.py](../benchmarks/run_premodel_hook_ab.py)。2026-09-13 的执行因账户模型用量上限而未开始，不能虚构全量结果。

## 宿主依据

OpenAI 的 MCP 文档明确描述“模型选择工具 → 服务返回 → 模型使用结果继续对话”的调用链。Codex Hook 文档说明 `UserPromptSubmit` 的 `additionalContext` 会被加入 developer context。插件打包文档说明 `hooks/hooks.json` 会被自动发现，同时安装插件不会自动信任 Hook，用户仍需审查当前 Hook 定义。
